# Embedding model benchmark — MindFlow corpus

Сравнение 9 бесплатных open-source эмбеддеров на реальном корпусе RAG MindFlow. Цель — выбрать модель для замены `multilingual-e5-small` по цифрам на нашем корпусе, а не по MTEB-маркетингу.

- **Корпус:** 2 321 чанк из `rag_chunks` (Кострыкин part 1/2/3 + Hefferon + MIT 18.06 + Яндекс). Исключены 150 мусорных чанков `auto_gelfand1971ru` (битый OCR).
- **Golden set:** 50 пар *(вопрос, ground-truth chunk_id)*, сгенерированы DeepSeek по случайным чанкам, стратифицированным по `source_id`. Вопросы — реалистичные студенческие («Как найти собственные значения матрицы через характеристическое уравнение?»). Файл: `infra/scripts/benchmark_data/golden_set.json`.
- **Стенд:** MacBook Apple M5, 32 ГБ RAM. Python 3.9, sentence-transformers 3.4.1, torch 2.8. MPS GPU использовался где возможно.

## Победитель: `Qwen/Qwen3-Embedding-0.6B`

**Цифры против baseline `e5-small`:**

| Метрика | baseline | **Qwen3-0.6B** | разница |
|---|---:|---:|---:|
| Recall@1 | 0.24 | 0.64 | **+167 %** |
| Recall@5 | 0.42 | 0.82 | **+95 %** |
| Recall@10 | 0.48 | 0.86 | **+79 %** |
| MRR@10 | 0.327 | 0.720 | **+120 %** |
| NDCG@10 | 0.364 | 0.754 | **+107 %** |

На 100 студенческих вопросов **Qwen3-0.6B находит правильный учебный фрагмент в top-5 в 82 случаях** против 42 у baseline. Это ровно в два раза.

**Цена:**
- Latency: 39 мс/запрос на CPU против 8 мс у baseline. На MPS GPU модель работает нестабильно (см. ниже), на CPU — стабильно ~0.5 сек/чанк при encode.
- Диск: 1.2 ГБ против 480 МБ — **меньше чем bge-m3** (2.2 ГБ).
- RAM: ~700 МБ peak resident size.
- Архитектура: LLM-based (Qwen2.5 backbone + mean pooling), требует `trust_remote_code=True` в sentence-transformers.

**Почему лидер именно эта модель:**
1. Семейство Qwen3-Embedding — действующий лидер MTEB Multilingual (8B даёт 70.58, 0.6B даёт 64.34). Семейство одно — стиль обучения один.
2. Instruction-tuning заточен под retrieval: префикс `"Instruct: <task>\nQuery: ..."` для запросов.
3. LLM-backbone лучше понимает контекст вопроса, чем bidirectional encoders типа BERT/XLM-R, на которых построены e5/bge-m3.

## Почему `bge-m3` — крепкое второе место, но второе

bge-m3 показал R@5=0.68 / NDCG=0.614 — отличный результат, +69 % к baseline. Но против Qwen3:
- R@5: 0.68 vs 0.82 (Qwen3 +14 пунктов)
- R@10: 0.80 vs 0.86 (Qwen3 ловит длинный хвост лучше)
- NDCG: 0.614 vs 0.754 (Qwen3 +23 %)

bge-m3 быстрее (9 мс/q против 39 мс/q) и универсальнее (dense + sparse multi-vector outputs из коробки). Это валидная альтернатива если latency критична — но качество ниже.

## Почему ВСЕ "топовые" англоязычные модели провалились

`nomic-v1.5` (R@5=0.04) и `mxbai-large` (R@5=0.04) — оба практически случайные. Это **не баг бенчмарка** (проверено: mxbai на CPU дал тот же 0.04). Причина:

- **nomic-embed-text-v1.5** — обучен на английских корпусах Nomic AI. Токенизатор и веса не охватывают кириллицу как «известные» токены. Русские слова распадаются на странные subword'ы, и similarity почти случайна.
- **mxbai-embed-large-v1** — англоязычный BERT-large, mxbai не позиционирует его как multilingual. На MTEB 64.68 в среднем по английскому, на русском без шансов.

**Главный вывод:** «Топ на MTEB» ≠ «топ на нашем русскоязычном корпусе». Нужны именно **multilingual**-модели:
- Qwen3-Embedding (любой размер)
- bge-m3
- multilingual-e5-*
- LaBSE-* (но не работает на длинных параграфах)

## Почему в семействе e5 ничего не помогает

Все три e5 застряли в зоне 0.36 ± 0.02 NDCG:
- `e5-small` (384D): 0.364
- `e5-base` (768D): 0.358 — *хуже* small
- `e5-large` (1024D): 0.335 — ещё хуже

Внутри семьи **размер не помогает**. Помогает только инструкция: `e5-large-instruct` = 0.378 (+0.04 над `e5-large`). Это известный эффект — encoder-only архитектуры выигрывают от right pooling + instruction, не от scale.

LaBSE-en-ru — единственная русско-ориентированная (по названию) модель — провалилась (R@5=0.20). LaBSE училась на коротких параллельных предложениях ru↔en для машинного перевода. У нас — длинные параграфы математического учебника. Модель не на ту задачу.

## Что меняем в коде

1. **БД миграция:** добавить колонку `embedding_1024 vector(1024)` в `rag_chunks` (параллельно старой `vector(384)`, без даунтайма). Готовый шаблон — `infra/db/migrations/024_rag_embedding_swap.sql.template`.
2. **Локальный эмбеддер** (для transformers.js в `apps/api/src/llm/localEmbedder.ts`):
   - **Основной:** `onnx-community/Qwen3-Embedding-0.6B-ONNX` — официальный ONNX-репозиторий Qwen3, доступен на Hugging Face. Совместим с transformers.js.
   - **Запасной:** `Xenova/bge-m3` — если что-то пойдёт не так в integration (Qwen3 LLM-style модель, transformers.js может потребовать обновления для KV-cache; на bge-m3 проверенный путь). Качество всё ещё +69 % NDCG над baseline.
3. **Префиксы:** для Qwen3 — `"Instruct: <task>\nQuery: ..."` для запросов, текст без префикса для документов. Для bge-m3 — без префиксов.
4. **Реингест:** 2 321 чанк × ~0.5 сек = ~20 мин на CPU. Один раз при миграции.

## Риски и что проверить

- **Railway / диск:** Qwen3-0.6B 1.2 ГБ модель + tokenizer ~150 МБ. С учётом Node deps это +1.5 ГБ к API-контейнеру. Проверить лимиты Railway.
- **Latency 39 мс/q на CPU.** Для API server с холодным CPU это значит ~0.05 сек на запрос — незаметно для UX. Прогретый — быстрее.
- **transformers.js поддержка Qwen3-Embedding** — критично проверить ДО миграции. Если не поддерживается — переключаемся на bge-m3, разница в качестве 14 пунктов R@5 (всё ещё в 1.6 раза лучше baseline).
- **Golden set 50 пар** — погрешность ±7 % на R@5. Лидерство Qwen3 (+40 пунктов R@5 над baseline) **в 6 раз** перекрывает погрешность. Выбор устойчив.
- **bge-m3 sparse-output** — позволит заменить BM25 в hybrid retrieval (см. `infra/db/migrations/019_bm25_or_query.sql`). Отдельная задача после миграции.

## Методика

1. **Корпус:** `SELECT * FROM rag_chunks WHERE source_id != 'auto_gelfand1971ru'` (2 321 строка).
2. **Golden set:** 50 случайно выбранных чанков, стратифицированных по `source_id`. Для каждого DeepSeek сгенерировал реалистичный студенческий вопрос (промт: «вопрос студента, не цитата, 5-20 слов», см. `infra/scripts/embed_benchmark.py:103`).
3. **Retrieval:** для каждой модели — embed корпуса + embed запросов с моделеспецифичными префиксами. Затем cosine similarity по нормированным эмбеддингам, top-10.
4. **Метрики:**
   - **Recall@K** — есть ли правильный chunk в top-K
   - **MRR@10** = mean(1 / rank), 0 если правильный chunk не в top-10
   - **NDCG@10** = mean(1/log₂(rank+1)) — учитывает позицию, главная метрика
5. **Воспроизведение:** `python3 infra/scripts/embed_benchmark.py --stage all`. Результаты каждой модели — в `infra/scripts/benchmark_data/results/<key>.json` (включает полный список рангов).

## Технические заметки

- На MPS (Apple M5 GPU) Qwen3-0.6B сильно тормозит и нестабилен (batch 1: 159 сек, batch 8: 278 сек, batch 9: 309 сек — замедление прогрессирует). На CPU тот же encode стабилен ~7-8 сек/batch.
- nomic-v1.5 на MPS: тоже нестабильно (batches от 6 до 178 сек) — но в среднем дотянул до конца.
- BERT-style модели (e5, bge-m3, mxbai, LaBSE) на MPS работают предсказуемо.
- Замер `+RAM` в таблице — *delta* RSS между прогонами в одной сессии, не peak resident size. Для реалистичной оценки потребления — Qwen3-0.6B ≈ 700 МБ, bge-m3 ≈ 600 МБ, e5-small ≈ 350 МБ.
