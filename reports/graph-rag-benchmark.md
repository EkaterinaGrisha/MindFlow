# Graph RAG benchmark — MindFlow corpus

Измерение влияния **Архитектуры #1 («Граф как фильтр/обогащение»)** на качество ответа AI-ментора. Граф НЕ меняет которые чанки нашлись — он добавляет **related-concept context** в prompt LLM. Поэтому retrieval-метрики (R@K/NDCG) не могут выявить эффект; единственный честный способ — сравнить сами ответы ментора с graph_context и без.

## Исходное состояние (важно)

При разведке нашли:
- `kg_concepts`: 44 концепта по 8 доменам (Линейная алгебра, Теория вероятностей, Статистика, ML, Алгоритмы, ...)
- `kg_edges`: 42 ребра, все типа `prerequisite`
- **У всех концептов `topic_slug = NULL`** — связи с чанками не существовало
- RPC `search_concepts_by_topic_slug` для всех 9 chunk topic_tags возвращала **0 концептов**
- **Текущий `graphRagBoundary.buildGraphRagContext` всегда возвращал пустой контекст** — то есть в проде graph RAG **никогда не работал**

→ Исправлено миграцией 026: проставлен `topic_slug` для 9 концептов (matrix-operations, rank-basis, eigenvalues, svd, derivative-gradient, limits-continuity, random-variables, bayes, hypothesis-testing). После этого Arch #1 ожил.

## Результаты бенчмарка

**Стенд:**
- 50 студенческих вопросов из golden set (тех же что в embedding-бенчмарке)
- top-5 чанков от Qwen3-Embedding-0.6B (текущий прод)
- 2 ответа на каждый вопрос: **A (baseline)** = retrieved_theory only; **B (graph)** = + graph_context
- DeepSeek-chat генерирует оба ответа (temperature=0.3, max 900 tokens)
- DeepSeek-judge сравнивает с randomized A/B order (защита от position bias)

| Вердикт судьи | Кол-во | % |
|---|---:|---:|
| 🏆 **baseline (без графа) лучше** | **25** | **50 %** |
| ответ с graph_context лучше | 19 | 38 % |
| равноценны (TIE) | 6 | 12 % |

**Из 50 запросов у всех 50 был непустой graph_context** — то есть Arch #1 работал технически для каждого. И всё равно проиграл.

**Если исключить ties:** baseline побеждает в **25 из 44 «решающих» сравнений = 57 %**. Граф в текущей форме **статистически вреден**.

## Почему текущий граф не помог

1. **Граф слишком узкий — 9 связанных концептов на 4 цепочки.** Связи внутри одной цепочки (matrix-ops → rank-basis → eigenvalues → svd) повторяются для большинства запросов. Для вопроса про теорию Галуа добавлять «изучи `rank-basis` перед, `svd` после» — нерелевантно, отвлекает.

2. **Topic_tags слишком общие.** Чанк помечен `eigenvalues`, но содержит, например, материал про жордановы клетки. Граф добавляет только высокоуровневую связь «пререк = rank-basis», а конкретный концепт жордановой формы не описан.

3. **Промт LECTURER форсит упоминать связанные темы.** Это делает ответ B длиннее и менее сфокусированным. Судья (DeepSeek) предпочитает плотные ответы.

4. **Многие запросы вышли за пределы 9 «школьных» тем MindFlow** (SO(2), силовские подгруппы, теория Галуа, факторкольца, числа Каталана). Для них вообще нет осмысленных related-concepts в нашем графе — граф добавляет ненужный шум.

## Главный вывод

**Архитектура #1 в нынешнем минимальном виде — в продакшен не годится.** Она:
- Работает технически (после фикса миграцией 026)
- Но **уменьшает** качество ответа в 50 % случаев и улучшает только в 38 %
- Net effect: **-12 пунктов win-rate** против отсутствия графа

Это **не значит**, что graph RAG плох — это значит, что текущий граф недоразвит:
- 44 концепта на ~2 300 чанков = слишком грубое разрешение
- 9 концептов в туре с topic_slug = только 5 % retrievable
- Все связи одного типа (`prerequisite`) — нет богатой семантики (`часть_от`, `обобщение`, `пример`, `аналог`, ...)

## Что делать дальше — 3 варианта

### Вариант A: расширить граф через LLM-extraction (Stage 2)
Прогнать DeepSeek по каждому уникальному чанку с задачей «извлеки концепты и связи». Получим граф из ~200-500 концептов с разнообразными отношениями. Затраты: ~$5-10 на DeepSeek + 2-3 часа работы. Затем повторить этот бенчмарк — если win-rate перевалит за 55 %, разворачиваем.

### Вариант B: убрать graph_context из LECTURER prompt
Поскольку текущая «связанные темы» подсказка чаще мешает, **отключаем её на проде** до момента когда граф будет достоин. `graphRagBoundary.ts` оставляем — он используется в UI для `related_topics` ссылок (это всё ещё полезно: «изучить дальше»).

### Вариант C: перейти к Arch #4 LightRAG-style
Параллельный поиск: dense по чанкам + traversal по графу → RRF слияние. Граф используется как **дополнительный сигнал для retrieval**, а не для обогащения промта. Качество retrieval может улучшиться, не зависит от длины промта. Затраты: 1 день работы. **Рекомендую начать с этого после Варианта A**.

## Куратору про граф RAG

Когда куратор спрашивает «почему ничего из graph RAG не работает» — теперь у вас есть **измеренный ответ**:
1. До 2026-05-23 в БД не было корректных связей `topic_slug` (баг). Граф ничего не делал.
2. После фикса (миграция 026): граф работает, но **минимальный — 9 концептов с 4 цепочками prerequisite**. Этого недостаточно для меняющего качество эффекта.
3. **План:** Stage 2 (LLM-расширение графа) → переизмерение → Stage 3 (Arch #4 hybrid). Если измеренная польза >55 % win-rate → разворачиваем в проде. Если нет — графа в LLM-promt не нужен, оставляем только для UI `related_topics`.

## Методика

1. Берётся тот же golden set (50 пар), что в `reports/embedding-benchmark.md`.
2. Для каждого запроса: top-5 чанков от Qwen3-Embedding-0.6B (cached в `infra/scripts/benchmark_data/candidates.json`).
3. Из retrieved chunks извлекаются `topic_tags` → `search_concepts_by_topic_slug` → `get_concept_neighbors` → формируется graph_context (зеркало `apps/api/src/llm/graphRagBoundary.ts`).
4. Два промта к LECTURER (системный из `prompts/lecturer.md`, упрощён для скрипта):
   - **A (baseline):** retrieved_theory only
   - **B (+graph):** retrieved_theory + graph_context
5. DeepSeek-chat генерирует оба ответа (temperature=0.3, max 900 tokens).
6. DeepSeek-judge (temperature=0) выбирает лучший. Порядок A/B рандомизирован.
7. Агрегируем процент побед graph vs baseline vs ties.

Воспроизведение: `python3 infra/scripts/graph_rag_benchmark.py --stage all`. Кеш ответов в `infra/scripts/benchmark_data/graph_rag_answers.json`, judges в `graph_rag_judges.json` — не пересчитываются при повторе.

## Затраты

- DeepSeek API: 50 × 2 ответа + 50 judges = 150 запросов × ~800 tokens ≈ $0.20
- Время: ~25 мин (ответы) + ~3 мин (judge)
- Кеш: всё сохранено для дальнейших экспериментов
